## Security/design audit — cross-wallet failover and degradation

**Scope/evidence:** Read-only source review; no edits, tests/builds, network calls, provider accounts, or devices. I apply the owner’s current tiering: Apple remains full-fidelity; Google/Samsung are real native adapters with a narrower declared subset. One domain entitlement must support simultaneous provider/device instances; none is an exclusive fallback.

### Confirmed current finding

**P1 — Authenticated Apple NFC passes can be issued without the sharing protection.** An authored template with `nfc.requiresAuthentication: true` and absent/false `sharingProhibited` only triggers a warning (`src/passkit/schema/validate-features.ts:131-132`). `validatePass` considers a pass valid if it has no errors (`src/passkit/validate.ts:88`); the build rejects only `!report.ok` (`src/passkit/build.ts:263-266`), so the pass can be issued. The rule test explicitly codifies warning severity (`src/passkit/schema/rules-features.test.ts:108-114`). Nearby checks block NFC without an `nfcEnabled` identity and validate message/key shape (`validate-features.ts:108-126`), but not this combination. Apple’s [Pass Builder schema](https://github.com/apple/pass-builder/blob/main/Protobufs/PassNFC.proto) says sharing prohibition prevents older OS versions from sharing a pass to bypass NFC authentication. **Required gate:** make this an error before signing and test both failing and correctly protected cases.

### Current implementation and limits

- **Apple-only baseline:** The approved architecture lists Google Wallet as a v1 non-goal (`docs/design/platform-architecture.md:11-25`); creation writes `.pkpass` (`src/worker/modules/passes/create.ts:84-105`); `/api/v1/nfc` has no handlers (`src/worker/modules/nfc/routes.ts:1-5`). No Google/Samsung adapter exists in the reviewed source. This is an integration gap, not a current cross-wallet vulnerability.
- **Credentials/screenshots:** PassBook generates a random 128-bit scan code (`src/worker/modules/passes/scan-code.ts:6-9`), uses it as a barcode and preserves it across publishes (`src/worker/modules/passes/scan-code.test.ts:63-84`; `passes/publish.ts:107-108`). A screenshot is therefore a copyable static bearer credential; entropy prevents guessing, not copying. A captured code can claim an otherwise valid pass; server gates may reject subsequent scans depending on repeat policy (`scan/act-check-in.ts:38-105`). This is a confirmed assurance limit, not a vulnerability absent a replay-resistant pass requirement. Do not call it rotating or screenshot-proof.
- **Online authority:** Scanner lookups are tenant-scoped (`scan/repo-lookup.ts:25,34-36`; `scan/resolve.ts:88-103`); evaluation checks current removed/voided/expired state (`resolve.ts:270-276`), and atomic gates are keyed by canonical pass/action/scope (`act-check-in.ts:38-105`; `migrations/0014_scan.sql:154-168`). Scanner settings and ledger specify `offline: false` (`scan/actor.ts:46-48`; `scan/ledger.ts:46`). Preserve this: every provider credential must resolve to the same domain pass and gate.
- **NFC fails closed today:** Android forwards encrypted VAS, but the PassBook bridge rejects `apple-vas` with an error (`src/web/scan/input/android-reader.ts:45-58`). `android/BRIDGE.md:3,50-56,64-68` states `vas.available` is false and reader timestamps/source are not proof. A device read must never itself become an accepted scan.
- **Revocation:** Apple removal publishes voided/expired content stripped of barcodes and NFC, but cannot erase an installed copy (`passes/remove-build.ts:23-33`); soft-deleted passes remain served voided for a seven-day grace (`passes/jobs.ts:14-16,31-44`). Online scanning checks current state; stale copies can still display. Provider update/deletion state is not proof that copies or screenshots disappeared.
- **Ownership/photos/device status:** Current pass rows hold one Apple `identity_id` and one owner; Apple registrations are per device/identity/pass (`migrations/0001_platform.sql:264-288,364-383`). The app imposes a 20-registration limit per pass (`apple/service.ts:24,101`), a PassBook limit—not an Apple platform limit. Creation rejects another organization’s identity (`identities/db-resolver.ts:104-109`; `passes/create.ts:78-80`). Member photos are opt-in for the Apple pass (`passes/member-photo.test.ts:82-110`) and scanner visibility is org/mode/template/role-gated (`scan/member-photo.ts:10-20`).
- **Customer delivery:** Email is `.pkpass`/Apple-badge only (`delivery/email.ts:72-74,115-118`); public add choice uses Apple-specific UA logic (`shared/device.ts:4-30`). In the new design, UA can recommend a likely provider, never hide other eligible choices or imply installation. Keep alternatives accessible. Emails should offer every eligible provider’s compliant branded CTA and accurate account/eligibility wording (Google [brand guidance](https://developers.google.com/wallet/generic/resources/brand-guidelines); Samsung [button integration](https://developer.samsung.com/wallet/api_new/addto/button.html)). Track “issued/add link available” separately from an observed installation.

### Required architecture invariant and failure modes

1. **One canonical entitlement, many instances.** Keep an authored provider-neutral domain record/revision—tenant, owner, validity, lifecycle, credential policy, data and consent—as the source of truth. Apple’s `.pkpass` is its full adapter; Google/Samsung need real native projections, previews, account/object or artifact state, add flows and lifecycle. Model provider account/object and any observable device installation separately. One entitlement may exist simultaneously across providers and devices. Provider instances must not create separate entitlements or redemption gates; unknown install telemetry stays `unknown`.
2. **Capabilities are semantic, not cosmetic.** Each feature is explicitly `required` or `optional`; adapters report `supported`, `unsupported`, `gated`, or `unknown`. An unsupported/unknown **required security semantic blocks only that provider instance** before issuance, with a visible reason. No automatic downgrade or fake fallback. Optional presentation loss must appear in provider-specific preview/confirmation. An outage or account rejection marks that instance pending/failed/stale without mutating the entitlement or other instances. The user may explicitly choose another eligible provider; failover never silently weakens assurance.
3. **Credential assurance:** distinguish static bearer, rotating/freshness-checked, and offline policy. Default to online verification of current tenant/owner/status/revision/time window and atomic replay/gate changes. Signatures and add JWTs authenticate issuance/save flow, not scanner freshness or current authorization. A rotation requirement must never map to static. Apple’s `PassBarcode` is static (`pass-types.ts:69-74`); updates are not rotation. Google documents TOTP rotating barcodes and warns that static fallback removes much of the security ([rotation guide](https://developers.google.com/wallet/generic/resources/rotating-barcodes)). The repo’s prior review records inconsistent Samsung dynamic-QR interval fields/units; treat equivalent assurance as unknown until resolved by partner/spec/device testing ([general guide](https://developer.samsung.com/wallet/addtosamsungwallet/barcodeqrcodepresentation.html), [event-ticket fields](https://developer.samsung.com/wallet/addtosamsungwallet/walletcards/eventticket.html)). Use server time and atomic replay state; client `readAt`/`source` is untrusted. Offline acceptance is disabled by default. If added later, specify maximum staleness and replay/revocation guarantees; deny when they cannot be enforced.
4. **Revocation, account, partner boundaries:** Canonical revocation immediately denies online redemption across all instances; provider updates/retries are tracked independently and cannot reactivate it. Scope provider credentials, account/class IDs, callbacks and object mappings to tenant/provider account; verify ownership server-side, not from client IDs. Keep canonical data, revisions and redemption authority outside partner accounts so offboarding cannot orphan entitlements. Google issuer onboarding, class sharing policy and Smart Tap issuer/certified-terminal gates are distinct ([onboarding](https://developers.google.com/wallet/generic/getting-started/onboarding-guide), [sharing status](https://developers.google.com/wallet/reference/rest/v1/MultipleDevicesAndHoldersAllowedStatus), [Smart Tap](https://developers.google.com/wallet/smart-tap/introduction/pass-configuration)). Apple NFC issuance and iPhone VAS-reading entitlements are separate ([Pass NFC](https://developer.apple.com/documentation/walletpasses/pass/nfc-data.dictionary), [ProximityReader entitlement](https://developer.apple.com/documentation/proximityreader/setting-up-the-entitlement-for-tap-to-pay-on-iphone)); Samsung NFC needs provider approval ([capabilities](https://developer.samsung.com/wallet/addtosamsungwallet/nfccapabilities.html)). Current `nfcEnabled` is a configured identity flag, not proof of platform approval.
5. **Sensitive data:** Keep photos/ID outside generic shared fields unless purpose, consent, provider template/account and retention are explicit. Google’s FAQ prohibits personal images on passes; Samsung `idPhoto` is template-specific, not a general image capability ([Google FAQ](https://developers.google.com/wallet/generic/resources/faq), [Samsung digital IDs](https://developer.samsung.com/wallet/api_new/walletcards/digitalids.html)). Never silently map a member photo into Google or Samsung ID data.

### Observable acceptance scenarios (proposed; not run)

- Issue one entitlement to Apple, eligible Google and eligible Samsung, across multiple devices. Each has independent provider status/preview, while all scans share one gate. Cross-tenant account/object/callback attempts fail; provider failure does not revoke sibling instances or lose canonical data.
- A rotating-required template produces no Apple or unverified-Samsung artifact/add action; Google succeeds only with verified rotation and no static fallback. Test time-window edges, screenshot replay, concurrent scanners and forged client timestamp/source. Static-required templates clearly identify themselves as copyable and obey configured repeat rules.
- Revoke, then present stale signed/cached artifacts and screenshots: online check-in denies immediately even if provider updates lag; offline denies by default. Optional omissions are visible in the preview.
- Google photo and unsupported Samsung `idPhoto` mappings are absent; Apple photo inclusion requires opt-in. NFC authentication without Apple sharing prohibition fails before signing; Google Smart Tap/Samsung NFC are unavailable without their account, partner, device/market and verifier gates.
- Public pages recommend a likely provider but keep all eligible alternatives accessible; unsupported UA does not hide them. Email shows compliant provider buttons only for eligible outputs and states account requirements; issuance/add-link is not shown as installed.
