# Hardware audit — scanner inputs (read-only)

**Scope:** `wallet` main repo at `8f5bee0` and `wallet-ios-scanner` worktree at `0458552`. Source inspection only: no builds, tests, runtime, or physical hardware checks were run.

**Architecture:** Web camera and HID input feed the scan input bus and normal scan API (`src/web/scan/camera/`, `src/web/scan/input/`, `src/worker/modules/scan/routes.ts`). Android adds a WebView/native bridge plus native camera permissions, NFC reader mode, and optional barcode broadcast. The iOS worktree adds a WKWebView bridge, camera permission handling, and a Core NFC NDEF reader.

## Supported hardware matrix

| Input | Implemented behavior and limits | Capability / verification status |
|---|---|---|
| **Camera** | Web scanner uses `getUserMedia` and ZXing WASM for QR, PDF417, Aztec, Code 128, Code 39, Codabar, EAN-13 and ITF. It requests an ideal front/back camera, optionally identifies a wide lens, and supports torch where available. Android grants WebView camera only for its trusted origin; iOS grants capture only to the trusted main frame. There is no explicit external-camera selection path. | Browser reports camera `available` if `enumerateDevices()` lists a video input; reporting does not prompt or establish permission. Native Android/iOS snapshots provide more permission detail. External camera attachment and actual camera behavior remain physically unverified. |
| **USB/Bluetooth HID** | Supported as OS keyboard-wedge input, not as a scanner connection. Web detects timed key bursts and maps physical key codes using a US layout. Android also provides a native text field requiring Enter/IME completion. iOS receives OS-delivered keys in the web scanner. USB and Bluetooth HID are both documented; no reader presence, model, or connection state is detected. | `keyboard.supported: true`, `connected: null`; this does **not** mean a reader is connected. Per-model, layout, focus, suffix, and reconnect behavior have not been physically verified. |
| **Vendor broadcast / SDK** | Android accepts a manually configured broadcast action and text extra. The receiver forwards its value through the same barcode bridge; there is no vendor SDK or built-in model-specific broadcast configuration. BCScan’s exact action is deliberately not guessed. iOS has no equivalent broadcast/SDK path. | `externalReader.connected` is unknown/null. Broadcast data is untrusted input. |
| **NFC / NDEF / VAS** | Android uses the device’s NFC adapter in foreground reader mode, NFC-A/B and ISO-DEP, skips NDEF checking, and implements a VAS-only APDU exchange that returns an encrypted cryptogram. It does not read NDEF. iOS implements a user-started Core NFC NDEF session and decodes well-known text/URI records (up to 2,048 UTF-8 bytes); it does not read Wallet VAS. | Android reports NFC availability separately from `vas.available` (always false). iOS reports NDEF availability and VAS unavailable. The iOS NDEF operation exists in the bridge, but the current UI has no caller for it. |
| **NFC reader accessories** | No raw USB/Bluetooth NFC reader, serial/SPP, proprietary BLE, or ExternalAccessory integration was found. Android VAS uses the device’s built-in NFC adapter; iOS Core NFC uses the iPhone/iPad reader. | Not detected or claimed as supported. |
| **Duo / customer display** | iOS worktree has optional Duo posture and camera-capture customer-display support behind iOS 27.1 availability checks. It is an output/layout feature, not an external scanner. Android reports no customer-display integration. | iOS capability varies by OS and system accessory availability; physical Duo behavior is unverified. |

## Findings

1. **P2 — Main web runtime disables camera based on configured reader, not usable hardware.** **Confirmed source.** Main `runtime.ts:76-85` disables camera for *any* non-`none` reader setting. Main `use-device-report.ts:12-15` also sets `nativeBarcode` from the mere presence of `PassBookNative`; the iOS shell injects that object (`wallet-ios-scanner/ios/PassBookScanner/ScannerViewController.swift:20-24`) but documents only HID wedge/NDEF, not native barcode (`ios/README.md:31-36`). Thus an iOS shell using the main web client can lose its camera fallback in barcode or NFC mode despite having no usable native reader. The iOS worktree has a capability-aware fallback (`src/web/scan/platform/runtime.ts:62-74`). **Fix/check:** gate camera disablement on the actual reader capability; verify iOS with `reader=barcode` and `reader=nfc`, `vas.available=false` keeps camera scanning available, while Android barcode mode uses native input.

2. **P2 — iOS and main-repo bridge/report contracts differ.** **Confirmed source; deployment impact conditional.** The iOS worktree’s device report includes a `native` object (`wallet-ios-scanner/src/web/scan/boot/use-device-report.ts:14-23`), accepted by its expanded strict schema (`wallet-ios-scanner/src/shared/contracts/scanning-sessions.ts:18-64`). The specified main repo’s strict `ScanDeviceCapabilitiesSchema` has no `native` field (`src/shared/contracts/scanning-sessions.ts:16-28`), and its `/device` route validates that schema (`src/worker/modules/scan/routes.ts:104-116`). Also, main `android-reader.ts:7-19,52-60` discards an incoming `method: 'nfc'` and forwards it as `wedge`, unlike the iOS worktree’s `native-reader.ts:7-20,43-81`. **If** the iOS shell is paired with the main web/worker revisions, capability reporting will be rejected and NDEF provenance lost. **Fix/check:** deploy the matching web, worker, and native bridge revisions together; confirm an iOS capability report is accepted and an NDEF event reaches the scan API as `nfc`.

3. **P2 — NFC is not an end-to-end acceptance path; NDEF UI is absent.** **Product recommendation, not an undocumented defect:** Android VAS capture is real source code (`NfcController.java:36-73`, `protocol/VasReader.java:11-40`), but the main web adapter rejects `apple-vas` with an error (`src/web/scan/input/android-reader.ts:52-58`); the NFC worker router is empty (`src/worker/modules/nfc/routes.ts:1-4`). The schemas in `src/shared/contracts/nfc.ts:4-41` are not a verifier. On iOS, `readNFC` is exposed by the runtime (`wallet-ios-scanner/src/web/scan/platform/runtime.ts:271-273`), but no UI call site exists; `readerUsable` also remains false while VAS is unavailable (`scan-loop.tsx:88-92`). Preserve the fail-closed behavior until verification exists. **Check:** a real Wallet VAS tap must never create an accepted ledger entry until authenticated payload decryption, tenant/pass mapping, replay handling, and atomic check-in are implemented and verified.

   Apple does provide Wallet loyalty-pass reads through ProximityReader `readVAS`, but this app has only the NDEF entitlement (`ios/PassBookScanner/PassBookScanner.entitlements:4-6`) and only reports `PaymentCardReader.isSupported`; it does not configure a reader session or call `readVAS` (`ScannerHardware.swift:13-23`). Apple requires the Tap to Pay entitlement and supported merchant/PSP configuration; returned VAS data still goes to the loyalty provider for processing. This is not a generic Core NFC VAS reader. [Apple: VAS loyalty passes](https://developer.apple.com/documentation/proximityreader/accepting-loyalty-passes-from-wallet), [Tap to Pay setup and entitlement](https://developer.apple.com/documentation/proximityreader/adding-support-for-tap-to-pay-on-iphone-to-your-app), [Core NFC NDEF reader](https://developer.apple.com/documentation/corenfc/building-an-nfc-tag-reader-app).

4. **P2 — Configured Android broadcasts can be spoofed by any local app.** **Confirmed source.** `MainActivity.java:265-268` registers the configured action with `RECEIVER_EXPORTED`; `:55-59` accepts its text extra without sender authentication. A local app that knows the action can inject a barcode into an active authenticated scanner and may trigger the configured automatic flow. The explicit counter-control is `android/BRIDGE.md:70`: treat broadcasts as untrusted and install only trusted apps on managed readers. **Fix/check:** add an enforceable sender boundary or retain an explicit managed-device restriction; test that an unauthorized app cannot produce a scan.

5. **P2 — Slow Bluetooth wedge profile is test-only.** **Confirmed source.** `WEDGE_SLOW` supports wider key gaps (`src/web/scan/input/wedge-detector.ts:21-38`) and tests show a 70 ms burst works only with that profile (`wedge-detector.test.ts:109-115`). Production runtime creates the wedge source without a profile override (`src/web/scan/platform/runtime.ts:169-175`), so it uses the standard profile. **Fix/check:** expose/select a slow profile or adapt detection; verify the slowest intended Bluetooth reader scans reliably through the same UI. This and standard US-layout/Enter requirements should be tested on each intended scanner.

## Strengths and limits

Camera reporting avoids permission prompts; native camera permission is scoped to the trusted origin/frame. Android distinguishes NFC hardware/reading from VAS verification, and native barcode results require a matching scan verdict before acknowledgement (`android/BRIDGE.md:47-56`). Android’s reader mode is foreground-only and explicitly skips NDEF; see [Android `NfcAdapter`](https://developer.android.com/reference/android/nfc/NfcAdapter). Direct USB host communication would require USB device discovery and permission handling, neither present here ([Android USB host guide](https://developer.android.com/develop/connectivity/usb/host)).

No physical checks were performed. Android’s acceptance checklist requires P400 model/firmware-specific ISO-DEP/VAS, broadcast, USB and Bluetooth testing (`android/ACCEPTANCE.md:5-18`); iOS likewise calls for device camera/NFC/keyboard checks (`wallet-ios-scanner/ios/README.md:17`). Missing evidence includes intended scanner models/firmware and BCScan action, actual P400 NFC compatibility, iPhone/iPad OS and entitlement/PSP eligibility, and Duo accessory availability. Test NFC-disabled/no-match/authentication-required and Apple Watch separately; do not infer physical support from source or emulator behavior.
