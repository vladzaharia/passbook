# Control UX redesign and mockups — 2026-11-07

**Status:** proposed target state; not implemented. This report is separate from the [general platform audit](../README.md), its security findings, and the [global priority report](../priority-report.md). It incorporates the completed [control/settings UX specification](control-ux-system.md), the admin/operator reviews, the other product audits, and the user's explicit direction: **preserve every current capability and add the new workflows; retain purposeful color, whimsy, motion, animation, and Buddy.**

- [Admin/control interfaces](../mockups/admin-interfaces.html): settings, organizations, scoped API keys, connection test, template release, pass issue/review and delivery/transfer.
- [Governance routes](../mockups/admin-governance.html): overview, status, audit, users/detail, Apple identities/detail, API keys, revocation and one-time disclosure.
- [Operations routes](../mockups/admin-operations.html): pass lifecycle, templates/import, connections, broadcasts, scanning resources and detail routes, test inbox, account and email management.
- [Customer portal](../mockups/customer-portal.html): portfolio, pass lifecycle/recovery, sign-in/account security, public pass states and sign-in email.

- [Prototype guide, capability-preservation matrix, visual critique log and screenshots](../mockups/README.md)
- Source inventory of current admin routes: [`nav.ts` and route inventory](../../../../src/web/lib/nav.ts); detailed coverage below.

The HTML is a local, non-networked visual prototype using synthetic data. Its buttons demonstrate target states and announce mock actions; they do not call product services, persist data, grant authority, create provider objects or prove enforcement. No product application source, route, test, or runtime behavior was changed. These selected frames are **additive proposals, not a replacement navigation shell**. Unmocked current pages and actions stay in the product.

## New target workflows — additive, not implied as implemented

- **Tenant administration:** explicit organization membership/RBAC; platform-wide authority remains separate; every action is server-scoped. Customer cross-issuer portfolio access remains separate from issuer-management rights.
- **Provider-neutral pass lifecycle:** one entitlement and admission rule; native Apple, Google and Samsung provider instances have independent artifacts, publication, update, registration/install observations, failures, retry, and retirement. No click, user agent, push acceptance, or provider-accepted state means “installed.”
- **Safe release and recovery:** semantic diff, audience/privacy projections, mode, provider/adapter revision, required capabilities and approved omissions are bound to an immutable reviewed candidate. Changes invalidate review; compare-and-swap blocks stale activation; rollback supersedes rather than rewinds in-flight generations.
- **Adaptive customer offers:** recommend Apple for eligible Apple devices, Samsung only for eligible Galaxy market/model/pass, Google for eligible generic Android. Device detection changes order only. Keep all eligible alternatives, truthful unknown installation state, and accessible requirements.
- **Multi-wallet email:** include each eligible provider's official asset, requirements and equivalent plain-text choice. The mockups use current Google/Samsung assets and the existing Apple badge path; do not recolor, crop, animate or imitate provider artwork. The Apple file is still the interim asset documented in `public/apple/README.md`; the official kit requires owner acceptance.
- **Browser barcode fallback:** an active pass page can present its exact primary barcode payload/format at a scan-friendly size. If a pass has no barcode, exposing its existing server-minted scan code as a QR requires a public-page projection; never mint a client-side code. The server scanner still resolves and authorizes every read. The current `BarcodeSvg` is explicitly labeled approximate/not for scanning, so production use requires scan testing; a web page does not emulate NFC or Wallet VAS.
- **Provider-neutral authoring:** canonical semantic fields, provider capability and native projections, front/details views, audience-aware scan display, customer-safe display preview, revision comparison, approval, release and provider-specific readiness.
- **Scanner privacy and operations:** role/audience projections are allowlisted server output; customer display is independently generic and read-only. Keep camera, USB/Bluetooth HID keyboard, manual code, lookup, undo and pause/end-shift actions. Uncertain outcomes remain unknown until reconciled; a new scan does not silently overwrite an unresolved result.

These capabilities depend on backend/security work already tracked in the general audit and the linked feature reports. The mockups do not claim those dependencies are complete.

## Visual and interaction contract

- **Preserve the PassBook kit.** Shared surfaces, semantic status colors, clear type hierarchy, focus-visible controls, existing iconography, save bars, dirty-dismiss protection, explicit confirmation verbs, and current route conventions. No second visual system.
- **Color with meaning.** Teal is the primary action/accent; success, warning, danger, information, and unknown remain distinct semantic states and are never conveyed by color alone. Both dark and light themes are designed. Pass colors remain separate from console accents.
- **Whimsy at real moments.** Buddy is decorative, state-appropriate, and appears at most once per view: a confirmed connection-test success and a confirmed scan success. Never use a happy Buddy for refusal, pending/unknown outcome, or system failure. The existing local Buddy art is used in both light and dark variants.
- **Motion with restraint.** Screen changes are brief; Buddy lands once with a transform/opacity-only beat. No ambient loops. Inputs/actions are immediate. Reduced motion removes the decorative Buddy animation and leaves the settled pose; scanner status, controls and verdicts remain visible.
- **Responsive scanner.** Desktop, phone portrait, short phone landscape, and 320px minimum frames preserve the context, result, recovery controls and dock. The scanner has an explicit return-to-session action when full-screen chrome is suppressed.
- **Accessibility.** Visible labels, tab semantics, named preview audiences, `hidden` panels removed from layout/focus, semantic verdict text, 44px touch targets, 16px touch inputs, wrapping, and no personal/staff data in customer output. The HTML prototype is not a keyboard, assistive-technology, contrast, camera, native-device or production-accessibility certification.

Normative implementation guidance remains in [UI consistency](../../../design/ui-consistency.md), [motion and expression](../../../design/motion-and-expression.md), and [scanner choreography](../../../design/scanner/buddy-motion.md).

## Complete route audit and redesign — 2026-11-08

Independent admin and customer design reviews found P2 coverage/usability gaps. The current prototypes now represent every current admin/customer route group in the matrix above, while remaining additive, synthetic and nonfunctional.

- **Admin:** retained settings essentials while Advanced adds detail; added responsive shared context and account controls; restored mobile table labels; represented pass version/device/check-in/connection/image/holder/delivery actions and distinct Wallet-remove versus holder-list lifecycle; added message scan targeting and audience review; added scanner, session and event details with add-device, assignment, edit, archive and readiness states.
- **Customer:** made collection states truthful; added multi-issuer passes, pagination, per-pass actions and eligible bundle affordance; made pending/unavailable wallet states non-actionable; restored refresh, link/QR, support, fields/events, status and confirmed holder-list removal; retained email verification/session management and safe sign-in return guidance.
