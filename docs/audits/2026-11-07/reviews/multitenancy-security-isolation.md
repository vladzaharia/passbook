1. **P1 · Warm template cache authorizes against stale organization ownership** — confirmed source; cross-isolate execution not reproduced. `CompositeTemplateRegistry.resolve` returns cached template/version data, including its mutable `orgId` (`src/worker/modules/templates/registry.ts:123-127`). Reassignment updates D1 and invalidates only the handling isolate (`src/worker/modules/templates/org-assignment.ts:33-34`). Pass creation authorizes using the resolved `template.orgId` (`src/worker/modules/passes/builder.ts:89-90`). A worker that cached a platform template can therefore continue authorizing an org-B `passes:write` key after another worker assigns it privately to org A; B can issue a pass using A’s template. Fresh read APIs check current ownership, so the vulnerable sink is pass creation/build. **Fix/acceptance:** do not cache mutable ownership metadata, or recheck it at authorization. Warm B’s cache, assign the template to A in another isolate, then assert B cannot create with either template resolution path while A can. Re-confirms the prior audit finding.

2. **P1 · Test-mode passes can pull live connector records** — confirmed source; same-org mode boundary, *not* an org-ID bypass. `POST /api/v1/passes` accepts `connectionId`, pins mode from the API key (`src/worker/modules/passes/routes-write.ts:56-60`), and `createPassRow` checks only that the connection is in the same org before setting pass mode (`passes/create.ts:71-83`). A test key can create or bind a test pass to its org’s live connection and call the scoped refresh route (`passes/routes.ts:154-163`). `connections/jobs.ts:27-29,61-67` checks org equality but not pass mode; scheduled record selection in `connections/repo-passes.ts:56-69` likewise has no mode predicate, and `applyConnectionRecord` mutates the linked pass. A key with `passes:read` and `passes:write` can then read the test pass’s live-source personalization. **Fix/acceptance:** test operations must not consume live connector data. Reject test/live bindings or provide an explicit test source, and enforce that boundary in refresh, poll, webhook and existing-link selectors. Test-key create/bind/refresh and scheduled sync must never copy live source fields into a test pass. Re-confirms the prior audit item.

3. **P2 · Tenant pass detail exposes global account email** — confirmed source disclosure. `GET /api/v1/passes/{id}` accepts `passes:read` and scopes the pass by org/mode (`src/worker/modules/passes/routes.ts:45-47,85-93`), but `detailOf` includes `ownerEmail` (`passes/detail.ts:164-176`) from `users.primary_email` (`passes/repo.ts:70-77`). `listBlockedUsers` also falls back to that email (`repo.ts:56-64`), as do last-void actor labels (`repo-devices.ts:40-60`). A tenant key reading its own pass can link an org-assigned/verified alias to a holder’s or actor’s private global account identity. **Fix/acceptance:** tenant responses expose only tenant-assigned contact data; keep global identity enrichment platform-admin-only. Test a private primary email plus tenant alias and blocked-user/void-actor fallback. Re-confirms and extends the prior `ownerEmail` finding.

4. **P2 · Shared-template reads expose other tenants’ issuance/rollout counts** — confirmed response; product intent for these aggregates is undocumented. Org keys with `templates:read` may read platform templates (`src/worker/modules/templates/routes.ts:43-50`; `templates/service.ts:80-86`). List and detail DTOs expose `passCount` and per-version counts; `repo-list.ts:54` and `repo-usage.ts:6-17` filter by template and mode, not org. Detail also exposes `passesOnOlderVersions`/`passesBlocked`; `repo-stale.ts:73-87` counts active, nondeleted passes across all orgs and modes. Shared template *content* is intentionally global; tenant pass usage/history is not explicitly so. **Fix/acceptance:** tenant keys see only their org’s counts, or counts are omitted; platform admins may see an explicitly labeled global aggregate. Seed A/B passes on one global template and compare key A/B list and detail counts, including Test-mode keys.

5. **P2 · Holder bundle bypasses org suspension/deletion delivery gate** — confirmed source. Authenticated `/api/v1/me/passes.pkpasses` packages active, unregistered passes by global `owner_user_id` (`src/worker/modules/me/routes.ts:64-72`, `me/repo.ts:79-95`, `me/service.ts:249-267`) without checking `orgs.status`. Public pass and bundle token lookups do require an active org (`public/service.ts:34-38`; `bundles/public-service.ts:13-18`). A holder can still download an affected org’s pass bundle after suspension/deletion. **Fix/acceptance:** gate each bundled pass on active org without removing the intentional cross-org set of a holder’s own passes. Suspend/delete A and verify A’s pass is excluded while their B pass remains. Re-confirms the prior audit finding.

## Yield 2 — Boundary, controls, target model

**Current architecture (decision/tradeoff, not a finding):** human admin is platform-global. `requireAdminRole` checks only the session role (`src/worker/platform/auth.ts:149-153`); org, connection, identity, scanner, audit and metrics routers use `requireAdmin`. No org-membership relation exists in the reviewed schema (`migrations/0001_platform.sql:1-58`). API keys can be org-bound and mode-bound; `org_id IS NULL` is an intentional platform wildcard under `assertOrgAccess`. Do not treat v1 global admins or explicit platform keys as an accidental tenant bypass; a stricter human org-admin model requires a new membership/role source.

**Positive controls verified:** org API keys stop resolving when their org is inactive; pass lists/by-ID writes enforce org and mode. Pass creation/binding checks connection org; `forOrg` rejects identities owned by another org but permits a global identity (`identities/db-resolver.ts:104-117`). Connector credentials use org AAD and are fetched with `WHERE id=? AND org_id=?` (`connections/secrets.ts:23-25,52-57`; `repo-runs.ts:50-66`). Bundles validate every member pass’s org and mode (`bundles/service.ts:80-110`). Scanning session devices have composite `(session_id,org_id)` and `(scanner_id,org_id)` FKs (`migrations/0024_scanning_sessions.sql:29-31`); admin scan scope validates org/event/templates. Org/mode filters also appear in pass lists, scan feeds, broadcasts, analytics dimensions and metrics cache keys. Pass idempotency is `(org_id,key)`; webhook dedupe is `(connection_id,event_id)`. Template R2 paths include org/platform segments; pass and pass-asset paths use globally unique pass IDs and are fetched after scoped row resolution. These controls do not repair the five findings above.

**Target guardrails:** add explicit `org_memberships(user_id,org_id,role/capabilities)` and a separate `platform_admin`; require an authorized `OrgScope` in management services/repos and default-deny tenant APIs/exports. Do not infer memberships from `created_by`, audit actors or global IdP admin roles—no authoritative org roster exists in this DB. Preserve `org_id=NULL` only as an explicit platform scope for shared templates/identities/keys, not as a generic tenant wildcard. Add composite tenant constraints/triggers for org-owned parent-child relationships (passes↔connections, bundle↔passes, scan/session/event/staff↔org/mode); use an explicit platform/global branch for shared templates/identities. Recheck mutable ownership at every authorization boundary and scope searches/counts/exports/caches/jobs by org and mode.

Customer identity is intentionally global: `users` and verified emails link the same customer to their own passes across orgs; `/api/v1/me` filters by `owner_user_id`, not org. Preserve that customer-only union while never using it as tenant-admin authority or disclosing global primary email to tenant APIs.

Wallet target is a domain entitlement with **many independent wallet/device instances**, not a provider override or one shared install state. Current `passes` stores Apple-specific `identity_id`, `pass_json`/`.pkpass` object and one logical pass history; Apple registrations can be multiple devices, while holder DTO currently flattens them to `inWallet` (`src/worker/modules/me/service.ts:33-61`). Keep Apple full-fidelity/first-class and preserve existing Apple identifiers, auth/download tokens, registrations and update cutover. Add real Google/Samsung 1.5-class native adapters/artifacts with a deliberately narrower declared capability subset, provider-specific previews/diffs/readiness/lifecycle, and per-instance install/update/revoke state; device availability and provider permissions stay explicit. Required unsupported security semantics fail closed; optional omissions are shown as explicit degradation. A holder may aggregate their own instances across orgs/providers, but tenant administration remains org-bound. Do not make one registration suppress another provider/device instance; keep current Apple Add-all behavior as a provider-specific choice.

**Acceptance matrix (proposed, not run):** (a) A/B tenant keys and org admins cannot read/write foreign IDs or infer them through list/search/count/export, settings, history, jobs or assets; platform principals remain explicit. (b) Cross-resource foreign-org inserts fail DB/service checks; cache warm/reassignment race fails closed. (c) Alias, blocked-user and actor identities never expose a foreign/global primary email; holder account still sees only their own cross-org passes. (d) test/live connector paths never transfer live data to test passes. (e) suspension/deletion gates public and holder delivery. (f) shared template content remains readable but usage counts are tenant-local. (g) one domain entitlement installs on Apple phone+Watch and concurrently on supported Google/Samsung devices; instance update/revoke/status is independent and no operation crosses org; Apple existing installs still update. Show provider-specific authoring preview/diff and unavailable features; required unsupported capability blocks issuance.

**Owner/legal unknowns:** no org membership roster/IdP mapping is present; owner must supply it. Decide whether global-template adoption counts are intentionally public and the permitted handling of holder primary email/verified aliases. Provider issuer accounts/entitlements and regional/legal terms require owner/legal approval; no production/provider access was performed.
