# Cloudflare service-fit follow-up

## Decision and evidence boundary

**Keep the current basic division of responsibilities; fix the application invariants before treating any Cloudflare service as a remedy.** Workers, D1, R2, Queues, Workflows, the existing scanner Durable Object, Cron, Email Sending and Analytics are reasonable fits for their present roles. There is no evidence that a wholesale move to KV, per-tenant databases, or more Durable Objects would repair the audited security or lifecycle defects. Add a per-credential coordinator only for a demonstrated strict shared upstream quota; use separate queues or databases only where measured isolation, capacity, recovery or residency requirements justify their complexity.

This is an architecture/operations follow-up to the [audit index](../README.md), especially [Cloudflare runtime](13-cloudflare-runtime.md) and [Cloudflare operations](14-cloudflare-ops.md), and the later tenant, business, authoring and wallet reviews cited below. It is **not a new production assessment**. The source audits distinguish confirmed code paths from conditional consequences and proposed, unexecuted interleavings. The prior local reproductions, including stale-email disclosure and scanner data leakage, have the exact limits in [verification](../verification.md); the local cross-organization holder smoke and partner-flow limits are in [business verification](../business-verification.md). This follow-up read existing reports and public Cloudflare documentation; it did not run tests, contact production, inspect a Cloudflare account or verify an external provider. Local reproduction is not provider or production verification.

**Plan, entitlement, pricing tier, actual configuration, deployment revision, use/quotas, DNS/egress reachability, WAF/Access enforcement, alerts, backup coverage, data residency, issuer approval and email/APNs delivery are all unverified.** Configured bindings in the source inventory establish intended integration, not deployed behavior. Numeric limits below are the publicly documented values reviewed on 2026-11-07, not account allocations or an SLA; they can change and more restrictive product, zone, provider or contract limits can apply.

## Minimal target architecture

1. **Workers** retain the HTTP APIs, public/holder and authoring surfaces, scanner decision endpoints, protocol handlers and small orchestration entrypoints. Authentication, current organization membership, authorization, mode, role and sanitized output are application responsibilities on every path, including jobs and WebSockets.
2. **D1 primary** is the authoritative store for tenant membership and grants, one domain entitlement, source/binding and lifecycle generations, the shared admission gate, provider-instance desired/applied state, audit and recoverable inbox/outbox/operation records. Use transactional batches and conditional writes for invariants within that database. A verified customer principal intentionally aggregates only *their own* passes across organizations; this never grants tenant administration or discloses global account data to tenant APIs.
3. **R2** holds immutable/versioned signed Apple packages, other real provider artifacts where appropriate, template assets and photos, accessed only through authorized capabilities. D1 stores references and authority. Neither an R2 prefix nor a difficult-to-guess object key is an authorization decision.
4. **Queues** transport retryable, bounded work by durable operation reference; **Workflows** checkpoint genuinely multi-step imports, synchronization, broadcasts and reissue. D1 is the recovery ledger, not queue depth or a Workflow's completion bit. **Cron** triggers bounded reconciliation, lease recovery and retention, reporting each hook separately.
5. Retain **`SCAN_HUB` Durable Object** for org/mode-scoped live fan-out and hibernating WebSockets. Keep authoritative scan, credential and revocation state in D1. No new KV by default. If a verified upstream contract needs one strict global rate across overlapping runs, a narrowly keyed DO is an option, not a replacement for authorization or D1 lifecycle fences.
6. Retain sender-restricted **Email Sending**, Apple APNs transport and provider-specific outbound adapters. **Analytics Engine** supplies sampled operational analytics; D1 and an appropriately retained audit/operation ledger supply exact business state. Workers Logs, external alert routing and tested recovery complete the operational layer.

## D1, R2 and async delivery boundaries

### Commit and artifact protocol

[D1 `batch()`](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch) is transactional within one D1 database: a failed statement rolls back the sequence. R2 object operations and a Queue send are **not part of that transaction**. [R2 direct reads, writes, deletes and lists are strongly consistent](https://developers.cloudflare.com/r2/reference/consistency/), but this does not make D1+R2 atomic; an outcome can be unknown after a transport failure, and a read returning 404 does not prove an earlier in-flight R2 write cannot still commit.

A suitable proposed sequence is:

1. Build deterministically against a pinned semantic/template/provider version and write a uniquely named, immutable artifact to R2. Record enough metadata to reconcile an ambiguous write; do not overwrite a shared mutable key.
2. In one D1 transaction, condition the commit on current tenant, mode, owner, status, binding, revision and relevant generation; record the artifact reference, audit and pending provider/delivery operations. A failed fence discards the *intent*, not blindly a possibly referenced object. On an ambiguous D1 insert/commit response, first reconcile the idempotency key and durable state; do not delete the object merely because an exception was observed. This is the [creation cleanup risk](13-cloudflare-runtime.md) and is **source-grounded inference**, not a reproduced D1 failure.
3. Dispatch from the durable outbox; sweep pending/lost dispatch and expired leases. Use a stable operation ID, org/mode, immutable scope and expected generation, not mutable recipient defaults or raw secrets, in queue/workflow state. Commit business completion/receipt before acknowledging the individual message. A failed send, timeout or crash leaves an operation recoverable.
4. Garbage-collect only provably unreferenced artifacts after a grace period that covers ambiguous commits, concurrent writers and the agreed restore window. Persist an erasure manifest **before** dropping the last D1 inventory; retry each R2 deletion to a recorded outcome. Align this with legal deletion/retention requirements.

For provider calls, commit local desired state and fan out each provider-instance operation independently. A stable provider idempotency key or conditional native operation is useful **only when the provider actually supports it**. If a response is lost after a possible remote success, query/reconcile by stable provider identity where possible; otherwise mark the outcome ambiguous for controlled recovery rather than claim exactly-once delivery or blindly duplicate. External wallet/email systems, D1 and R2 do not share a distributed transaction. Revocation should deny online admission locally first; asynchronous native updates can remain pending or fail without reactivating the entitlement. A remote device can keep an old offline copy.

### Queues, Workflows and Cron

- Cloudflare Queues are [at least once](https://developers.cloudflare.com/queues/reference/delivery-guarantees/) after a successful write and [do not guarantee publish order](https://developers.cloudflare.com/queues/reference/how-queues-works/). Duplicates, out-of-order records, lease expiry, queue-send failures, retry exhaustion and retention expiry must be handled. Individual `ack()` after durable application avoids replaying already-completed siblings in a failed batch; it does not solve an external success followed by a lost local acknowledgement. Without a configured DLQ, exhausted messages are deleted; a DLQ is itself a finite-retention queue, not a permanent ledger. [Batching, retries and delays](https://developers.cloudflare.com/queues/configuration/batching-retries/) · [DLQ](https://developers.cloudflare.com/queues/configuration/dead-letter-queues/).
- A deliberate quota/budget deferral should persist `not_before` and the operation's pending state, then acknowledge the wake-up only after that persistence; a bounded sweeper/dispatcher sends a new wake-up when due. This avoids spending delivery attempts before execution. Do not reset provider failure counts or bypass actual retry limits when doing so. Honor numeric and HTTP-date `Retry-After`, provider cooldown and per-credential fairness. A higher `max_retries`, queue split, or delayed `retry()` alone is not this fix.
- Workflows persist checkpoints and [retry individual steps](https://developers.cloudflare.com/workflows/build/sleeping-and-retrying/); [steps should be idempotent](https://developers.cloudflare.com/workflows/build/rules-of-workflows/). A restarted/retried step may repeat external effects before its successful result is checkpointed. Persist small cursors/references, not secrets or whole artifacts; distinguish completed execution, partial business failure, superseded work and success. Continue until a null cursor or persist an explicit continuation; never turn a page limit into success.
- Cron is a **wake-up**, not proof every maintenance hook completed. [Cron uses UTC and schedule changes may take up to 15 minutes to propagate](https://developers.cloudflare.com/workers/configuration/cron-triggers/). Checkpoint bounded batches against remaining query/time budgets, record each hook's success/failure/skips and last successful completion, and alert on overdue work independently of the scheduler heartbeat. A failed retention batch must not consume or erase its object-deletion inventory.

## Caching, Durable Objects and strict quotas

**Authorization freshness:** Fetch mutable template owner/archive state, organization status, membership/grant and credential generations from authoritative D1 primary state for a new action; include the relevant expected state in the committing SQL. Cache immutable template payload, public static assets or provider-neutral rendering data by immutable revision only. A cached payload is not evidence of permission to use it. If caching includes org/mode/provider metadata for non-authoritative display, scope keys and specify staleness and invalidation explicitly; never share tenant-sensitive artifact responses through a public CDN cache. No TTL makes a revoked permission immediately safe.

[KV is eventually consistent](https://developers.cloudflare.com/kv/concepts/how-kv-works/): changes and even negative reads can remain cached in another location for **60 seconds or longer**. It does not supply atomic cross-key transactions. Do not move authorization, revocation, dynamic tenant ownership, redemption or exact quota counters into KV. Direct R2 binding/S3 API reads are strongly consistent, but an R2 custom domain with CDN caching can still serve a deleted/overwritten object or a cached 404 until purge/expiry; [R2 explicitly documents this distinction](https://developers.cloudflare.com/r2/reference/consistency/#caching). Versioned public assets can be cached; private passes/photos and bearer capabilities need authorization and a safe no-store policy. Purging a CDN is not a substitute for credential revocation.

[D1 read replicas](https://developers.cloudflare.com/d1/best-practices/read-replication/) can improve noncritical read latency/throughput only when callers use the Sessions API; raw binding queries remain on the primary. Replicas can lag. A session supplies sequential consistency, not universal freshness across independently initiated sessions. Use primary/latest reads and final conditional commits for grants, deletion, scanner admission and provider authority. Consider replicas only for measured, explicitly stale-tolerant queries; enabling them alone does not fix the warm-isolate authorization bug.

**Existing live state:** `SCAN_HUB` already has a coherent per-org/mode fan-out use case, bounded history and hibernating sockets ([runtime review](13-cloudflare-runtime.md)). Keep recipient reauthorization and a separate customer-safe projection. Reconnect, replay, revocation and scanner event correlation remain application problems. [Hibernation](https://developers.cloudflare.com/durable-objects/best-practices/websockets/) saves idle duration charges but resets in-memory state and does not preserve a business ledger by itself.

**When a new DO is justified:** The current connection pacing is per run, while scheduled, manual and per-pass jobs can overlap. If the actual partner contract requires one strict aggregate quota, all cooperating callers for the **same upstream credential/account** can route through one credential-keyed DO with an atomic, persisted token/leaky-bucket or matching provider algorithm. Include retry/cooldown, `Retry-After`, idempotent reservations and tenant fairness if multiple tenants share that credential. Fail safely if the coordinator is unavailable; ensure no alternate caller bypasses it. A D1 transactional counter/lease may suffice at lower rates and should be compared on contention, latency, fairness and operational cost. A DO does not coordinate external systems or another account that bypasses it; local counters or a single run's sleeps do not establish a global limit.

A DO is a single-threaded coordination point **per object**, not an automatic transaction across asynchronous external calls or D1/R2. Explicitly serialize/atomically persist the limiter decision; do not assume that `await` cannot interleave request handling. Expect network distance, a hot-key/overload and availability dependency; shard by truly independent credential, not by tenant when tenants share one upstream quota. [DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/) charges requests, active/non-hibernatable wall-clock duration and storage/operations; pending I/O and non-hibernating sockets can increase duration. There is no demonstrated reason for a per-pass DO or a global DO for all platform work.

## Outbound deadlines, abuse and quotas

The current safe-fetch control already requires HTTPS/443, rejects private address answers/direct IPs, blocks redirects and caps response bytes; the audit did **not** show private-network access. However, the separately checked DNS answer is not bound to the subsequent `fetch()` destination, and the configured timeout starts after sequential DNS. Fix both *as independently evidenced design issues*:

- Create one monotonic deadline and propagate the caller's abort signal before save-time validation, DNS and HTTP; an already-aborted request must do no lookup. Bound resolver attempts, redirects (prefer no redirects; otherwise validate every hop), request/response bytes, decompression, concurrency, queue work and total retries. Close/cancel unused response bodies.
- Prefer an explicit allowlist of approved partner endpoints. For arbitrary approved hostnames, use a transport/egress mechanism that enforces destination restrictions **at the actual connection**, or fail closed where the Workers transport cannot provide the required guarantee. A validation-time DNS lookup followed by fetching the original hostname is not DNS pinning. Cloudflare's [known issues](https://developers.cloudflare.com/workers/platform/known-issues/#fetch-to-ip-addresses) say Worker subrequests cannot simply fetch a direct IP URL, so do not prescribe that as a drop-in fix. The feasibility and deployed egress policy need separate evidence; do not add an unverified proxy and call it safe.
- Layer WAF route/IP abuse mitigation and a pre-auth Worker limit before expensive D1 credential resolution, then use org/key/connection-specific accounting after authentication. Protect critical auth, revocation and scanner operations from bulk-work starvation; apply fair per-tenant intake, queue/backlog and provider budgets. A CPU cap or billing alert alone is neither a hard account spend cap nor a strict global request budget.
- [Worker rate-limit bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/) use **10- or 60-second** periods and approximate, location-local counters; [WAF rate limiting](https://developers.cloudflare.com/waf/rate-limiting-rules/) may allow excess requests during propagation and varies by zone plan. A strict quota needs explicit coordination and upstream 429 handling. Separate provider quotas, app query budgets and Cloudflare limits; do not present one as another.

## Security perimeter, secrets and sensitive surfaces

Use [Access](https://developers.cloudflare.com/workers/configuration/cloudflare-access/) narrowly for operator-only administration, previews and break-glass paths where clients and policy permit it. Do not apply blanket Worker-level Access to public holder links, Apple Wallet service, partner webhooks, scanner pairing or unattended machine endpoints without an alternative authenticated design. Cloudflare states Worker-level Access currently rejects WebSocket upgrades; an appropriately scoped hostname-based Access application is the documented alternative, subject to testing the intended clients. An Access identity is not itself a tenant membership; the application must validate principal, org, role, mode and object authorization. Pay attention to alternate routes/hostnames and to Access identity propagation across service bindings/static assets as documented.

WAF and managed challenges are perimeter controls, not protection against a valid-but-overprivileged tenant, a malformed DTO or an unsafe background consumer. Respect wallet provider and webhook clients that cannot solve interactive challenges. [Turnstile](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/) requires server-side Siteverify; tokens are single-use and valid for 300 seconds. Validate the intended hostname/action as applicable, fail safely on errors and provide a recovery path. The local widget error in [verification](../verification.md) is not evidence of a production Turnstile problem.

Retain Worker secret bindings and record/tenant/kind-bound envelope encryption; [required secret names](https://developers.cloudflare.com/workers/configuration/secrets/#validate-secrets-before-deploy) do not validate the values. A separate Secrets Store is optional and not a substitute for access policy, rotation, AAD-aware migration, old-key availability or an offline recovery plan. Keep shared Apple-team APNs/signing authority platform-managed until explicitly delegated; a tenant must not rotate another tenant's shared credential. Logs, queue payloads, Workflow parameters and status must exclude bearer links, pass JSON, tokens, credentials, photos and unneeded partner records. Central export and staff access require their own tenant and retention controls.

## Recovery, observability and residency

**Coordinated recovery design, to be exercised in isolation before relying on it:**

1. Define RPO/RTO, accountable operators, acceptable provider staleness and legal retention/deletion holds. Inventory D1, every referenced R2 prefix/object and artifact version, applicable credentials/KEKs, source and provider accounts, queue/Workflow operations and scan state. Maintain a recoverable post-backup revocation/erasure and operation journal outside the D1 snapshot being rewound.
2. Quiesce writes, dispatchers, queue consumers, Workflows and relevant cron hooks; record a recovery point and fence in-flight/old-generation work. Protect other tenants: restoring a shared D1 database in place is not tenant-selective recovery.
3. Restore a consistent D1 point and matching preserved R2 object versions plus the correct keys. Reconcile every restored reference, hashes, tenant grants and provider-instance desired/applied state. Replay post-backup revocations, erasures, credential rotations and authorized later changes **before** reopening, and suppress duplicate emails/provider operations; reconcile external providers rather than assume they rewound. Define how already-sent mail and offline wallet copies are disclosed.
4. Prove restored live/test and tenant isolation, scanner denial for revoked credentials, availability of retained artifacts, re-dispatch of pending work and key decryption; verify erasure/hold exceptions and record measured RPO/RTO. Reopen incrementally only after these gates. A D1 bookmark alone does not preserve R2 or keys.

[D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/) is available on the documented production backend, but restoring overwrites the database in place and cancels in-flight queries. It is not an R2 backup. Consider immutable object keys plus a separately protected backup/preservation tier and, where retention policy permits, [R2 bucket locks](https://developers.cloudflare.com/r2/buckets/bucket-locks/). Locks prevent overwrite/delete during retention and take precedence over lifecycle deletion; they are **not** automatic cross-service snapshots, must not defeat privacy erasure/retention commitments, and can be administratively changed. Separate backup credentials/account and encrypted off-platform keys reduce shared-failure risk; verify actual coverage rather than infer it.

**Operational signals:** Persist sanitized per-tenant/mode operation and per-provider outcomes; show attempted, accepted, applied, saved/registered/observed and unknown separately. Alert on unresolved terminal failures even after a DLQ is drained, oldest outstanding inbox/outbox age, retry/deferral exhaustion, stale source cursor, partial/superseded Workflow, each overdue/failed cron hook, unsafe auth-denial spikes, DNS/deadline failures, D1 overload, R2 missing objects, KEK readiness, sender suppression/bounce and provider 429/error. Record correlation IDs without credential or personal payloads; route alerts to an owner with acknowledgement and escalation. Test both Analytics Engine and D1 fallbacks so missing scan projections are **unavailable**, not false zero.

[Analytics Engine samples at write and query time](https://developers.cloudflare.com/analytics/analytics-engine/sampling/); weighted estimates and an appropriate index are useful for monitoring, not a complete security audit trail, exact admission ledger or billing authority. [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) have plan-dependent short retention and sampling/cost implications; choose redacted structured events, necessary retention and export/alerting intentionally. Do not simply enable full request/URL capture: links and tokens may be sensitive. Cloudflare [Email Sending observability](https://developers.cloudflare.com/email-service/observability/) can assist diagnosis, but accepted/sent, delivered, opened, saved and installed are distinct and may be unknown.

**Residency:** [D1 jurisdictions](https://developers.cloudflare.com/d1/configuration/data-location/) and [R2 jurisdictions](https://developers.cloudflare.com/r2/reference/data-location/) are creation-time constraints; location hints are best-effort, not residency guarantees. D1 jurisdiction restricts where the database runs/stores data, not all Worker processing locations; R2 documentation also lists jurisdiction-specific integration limitations. Trace queue, logs, backup, compute, identity, email, APNs and other wallet providers separately. Jurisdiction, legal basis, contractual processor terms and actual account configuration were not verified.

## Staged execution and evidence gates

These are **recommendations and proposed acceptance gates, not work performed by this report**. Application/security owners own correctness; platform operations owns account configuration, monitoring and recovery; product/provider owners own native semantics, approved assets and customer-facing claims.

1. **Contain release blockers first.** Triage against the deployed revision; consider narrowly pausing affected sends, live connector paths, unsafe administrative/scanner actions or NFC issuance where the owner judges exposure unacceptable. Fix and deterministically reproduce/retest former-holder email and transfer capabilities, test/live source isolation, scanner data/role/capacity/event fences, current tenant ownership, OIDC proof, deletion/binding fences and required NFC policy. Preserve intentional holder aggregation. WAF/Access can reduce exposure but do not close these gates.
2. **Make accepted work recoverable and ordered.** Implement transactional inbox/outbox, ambiguous-write reconciliation, safe R2 artifact lifecycle, source revisions/cursor fairness, per-item idempotency and due-operation scheduling; fix workflow version/target/cursor/partial-outcome logic and safe-fetch deadlines. Exercise crashes between every D1/R2/queue/provider boundary, duplicate/out-of-order input, budget exhaustion, 429 backoff, retry exhaustion and account/mode changes. Require either the correct result or a visible durable recoverable failure.
3. **Make operations and recovery truthful.** Repair per-hook, DLQ, analytics and KEK reporting; define alerts, retention, privacy and budgets; resolve deploy/secret preflight inconsistencies. In an isolated environment exercise the coordinated D1/R2/KEK restore, retained-object and erasure manifests, post-backup revocations, external reconciliation and unrelated-tenant preservation. Record measured outcomes and alert delivery, not just configured dashboards.
4. **Cut over tenancy and provider architecture safely.** Establish explicit org memberships and service-principal/grant migration with no inferred roster; enforce org/mode at all control/data/asset/job layers. Preserve Apple pass type/serial/token/service route, device registrations, immutable histories and full-fidelity output. Introduce a semantic entitlement with many provider/account/device instances and independent statuses; implement real Google/Samsung native operations and audience-safe nontechnical authoring/previews. One shared redemption gate remains authoritative. Demonstrate required-feature fail-closed behavior and isolated provider failures before enablement.
5. **Prove customer channels and account prerequisites.** Verify eligible-provider web recommendations with reachable alternatives, all official branded email actions and exact per-provider requirements, unknown installation states, sequential bundle completion and multi-device/shared-gate behavior. Separately obtain owner evidence for Cloudflare plans/WAF/Access/Turnstile, quotas and location, verified sender and actual external delivery, Apple/APNs credentials, Google issuer and Samsung partner approval, and physical-device/provider behavior. Canary per tenant/provider with rollback that continues servicing updates/revocations for already-issued instances; only then make production readiness or SLA claims.
