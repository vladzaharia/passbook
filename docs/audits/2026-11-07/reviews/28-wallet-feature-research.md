# Cross-platform wallet feasibility audit — 2026-11-07

**Inspected:** PassKit schema, templates/behaviors, signing/build and Apple update/removal paths in `wallet`; Android reader and iOS scanner documentation in the iOS worktree; Apple, Google and Samsung developer documentation. **No tests, builds, hardware, partner accounts, entitlements or production services were exercised.**

**Summary:** PassBook currently issues Apple `.pkpass` files only. Google Wallet is feasible through a separate class/object API; Samsung Wallet is also possible, but depends on partner setup, templates and device/country availability. They are not interchangeable renderers for Apple’s schema. Preserve the requested credential and revocation guarantees per provider—never silently substitute a weaker barcode or sharing policy.

## Findings

1. **P1 — NFC authentication can pass validation without the required share prohibition.** **Confidence: confirmed-source.** `validate-features.ts:131-132` emits a warning when `requiresAuthentication` is true but `sharingProhibited` is not; `rules-features.test.ts:108-114` codifies warning severity. `validate.ts:88` defines validity as “no errors,” so `build.ts:263-266` still builds that pass. Apple’s [Pass Builder schema](https://github.com/apple/pass-builder/blob/main/Protobufs/PassNFC.proto) says `sharingProhibited` prevents older iOS versions from sharing a pass and bypassing NFC authentication. **Impact:** an NFC-authenticated credential can be issued without that protection. **Fix:** make the missing prohibition a blocking error when NFC authentication is required. **Acceptance check:** such a template fails before signing; setting both properties passes validation.

2. **P1 — Cross-wallet security requirements need a fail-closed provider gate.** **Confidence: confirmed-source; integration risk is inference.** The Apple type is a static `PassBarcode` (`pass-types.ts:69-74`); the engine’s barcode fallback warning is only for OS symbology compatibility (`validate-barcodes.ts:57-68`), not credential strength. Google’s rotation guide explicitly warns against static fallback; Samsung’s dynamic-QR docs conflict on interval units/casing. **Impact:** mapping a required rotating credential to a static barcode would silently weaken screenshot/replay protection. **Fix:** model required redemption strength explicitly; reject issuance when a provider cannot supply it, and do not attach a weaker fallback. **Acceptance check:** a rotating-required fixture fails for Apple and unconfirmed Samsung configuration; Google issues no static fallback.

3. **P1 — Native provider support is a separate product integration, not a PassKit export option.** **Confidence: confirmed-source.** The architecture declares Google Wallet out of scope (`docs/design/platform-architecture.md:21-25`); `PassJson` is PassKit-shaped (`pass-types.ts:213-272`), and `build.ts:257-260` injects Apple identity, authentication token and web-service URL. No native Google/Samsung provider adapter was found in the inspected code. **Impact:** current issue, update and template paths do not provide Google or Samsung saves. **Fix:** add provider-specific issuance/update adapters and explicit capability reporting; preserve Apple’s existing pass format. **Acceptance check:** the same domain fixture produces distinct, provider-valid objects without dropping unsupported requirements.

4. **P1 — “Revoked” does not mean an offline copy is immediately unusable.** **Confidence: confirmed-source.** Apple removal strips barcodes/NFC and voids the latest pass (`remove-build.ts:10-32`), but devices must receive/fetch that update; the service retains deleted passes for seven days (`jobs.ts:15-16`). Google documents no object-delete API; Samsung documents a `DELETED` state. **Impact:** an old, offline pass or captured barcode may still be presented. **Fix:** have the verifier check authoritative status/replay state online, or use bounded-lifetime credentials with explicit offline limits; define revocation per wallet. **Acceptance check:** an old credential is denied after revocation, and offline behavior is explicitly tested and bounded.

5. **P2 — Photos, relevance and availability are not portable feature parity.** **Confidence: confirmed-source.** PassBook’s member photo is an Apple thumbnail flow (`member-photo.ts:138-160`); Google prohibits personal pass images, while Samsung documents photos only for particular templates. Apple’s time/location/beacon relevance (`relevance-window/index.ts:38-57`) is not equivalent to Google’s Wallet-controlled nearby notifications or Samsung’s location fields. Apple NFC, Google Smart Tap and Samsung NFC each have separate approval/reader gates. **Fix:** expose per-provider capability/omission status; never upload a personal photo to Google. **Acceptance check:** tests verify omitted Google photos, supported Samsung template limits, and location/relevance behavior only on eligible providers/devices.

**Alternatives and counter-controls:** A shared web/PWA barcode plus camera/HID scanner can cover devices without Wallet-specific support, but it is not a native wallet, needs a verifier, and does not provide equivalent NFC or Lock Screen behavior. The existing Android reader leaves Apple VAS cryptograms unverified and does not implement Google Smart Tap/offline verification (`android/README.md:1-38`); the iOS scanner shell does not read Wallet passes (`/private/tmp/wallet-ios-scanner/ios/README.md:1-34`). The PassKit builder does block NFC on non-enabled identities and validates key shape/message length (`validate-features.ts:107-130`); removal strips actionable fields. **Uncertainty:** Samsung dynamic-QR semantics and market/device support require partner confirmation; Google market-specific issuer availability and Apple entitlement approval were not verified. Vendor documentation reviewed **2026-11-07**; no runtime or hardware verification was performed.
