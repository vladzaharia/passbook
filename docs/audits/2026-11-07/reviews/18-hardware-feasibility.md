# Hardware Audit 2 — Scanner Hardware Feasibility

**Inspected boundaries:** PassBook at `8f5bee0` and iOS worktree at `0458552`; shared scanner contracts/runtime, Android P400 reader and bridge, iOS native shell and web scanner; official Apple and Android documentation. **Read-only:** no edits, builds, tests, device runs, production calls, or signing-material inspection.

**Summary:** The model usefully separates NFC hardware/protocol support from an end-to-end VAS verifier, and correctly treats HID scanners as keyboard input rather than claiming connection detection. iOS Wallet VAS is not implemented: the iOS app reads NDEF only, while Apple’s documented Wallet-loyalty path is entitlement- and payment-provider-gated. The iOS NDEF reader also has no caller in the scanner UI. iPad USB cameras and iPhone Duo features are plausible, documented platform paths, but their behavior in this app remains device-dependent and unverified.

**Architecture / key files**
- `/private/tmp/wallet-ios-scanner/src/shared/contracts/scanning-sessions.ts:15-58` defines native camera, keyboard, NFC, VAS, external-reader, customer-display, and Duo-layout capabilities. `src/web/scan/boot/use-device-report.ts:14-26` adds browser-observed camera/input data.
- `android/app/src/main/java/im/plrs/passbook/reader/{MainActivity,NfcController}.java` reports capabilities and handles Android NFC reader mode; `android/app/src/main/java/im/plrs/passbook/reader/protocol/VasReader.java` implements the VAS APDU exchange. `android/BRIDGE.md:42-58` documents the wire capability meanings.
- iOS native behavior is in `/private/tmp/wallet-ios-scanner/ios/PassBookScanner/{ScannerHardware,NFCReader,ScannerViewController}.swift`; web input is in `src/web/scan/input/native-reader.ts` and camera decoding in `src/web/scan/camera/`.

## Findings

1. **P2 — iOS Wallet VAS is gated, not an available scanner feature.** **Confirmed source.** iOS reports `vas.available: false`; its native NFC format is `ndef`, and the local entitlement file requests only NDEF (`ScannerHardware.swift:19-22`, `PassBookScanner.entitlements:5`). The app checks `PaymentCardReader.isSupported` but does not prepare a reader or call `readVAS` (`ScannerHardware.swift:20-21`). Apple documents Wallet loyalty reads through ProximityReader/Tap to Pay, with a required Tap to Pay entitlement, PSP-provided token, and supported region/provider; `isSupported` means iPhone XS or later, not entitlement or OS readiness. The separate Core NFC `NFCVASReaderSession` documentation also says it requires an Apple entitlement. Thus **iPad is not a ProximityReader VAS target**, though it can support NDEF. Android instead implements reader-mode A/B + IsoDep and returns encrypted VAS data; its verifier availability is also false (`NfcController.java:50-72`, `MainActivity.java:342-353`).
   **Recommendation / acceptance:** Keep iOS `vas.available` false until the approved entitlement/provider integration and server verification exist. On eligible, entitled iPhones, verify configured NFC passes, provider response, and server decision; verify iPad and unentitled devices cannot show an accepted Wallet result. Sources: [Apple Wallet loyalty passes](https://developer.apple.com/documentation/proximityreader/accepting-loyalty-passes-from-wallet), [Tap to Pay entitlement](https://developer.apple.com/documentation/proximityreader/setting-up-the-entitlement-for-tap-to-pay-on-iphone), [device support](https://developer.apple.com/documentation/proximityreader/paymentcardreader/issupported), [Core NFC VAS session](https://developer.apple.com/documentation/corenfc/nfcvasreadersession).

2. **P2 — iOS NDEF reading is implemented but not reachable from scanner UI.** **Confirmed source; product limitation, not a VAS bug.** `NFCReader.start` opens an NDEF sheet and extracts text/URI (`NFCReader.swift:10-21,43-59`); `ScannerViewController` accepts `nfcRead` (`:141-143`), and the native adapter exposes `readNfc` (`src/web/scan/input/native-reader.ts:106`; runtime `:271-274`). But no scanner UI caller invokes it; the iOS README explicitly says the current UI exposes no NDEF action (`ios/README.md:32-36`). `nfc.available` therefore describes tag-reading capability, not an operator-usable scanner action.
   **Recommendation / acceptance:** If NDEF scanning is in scope, expose a separate, explicit NDEF action; otherwise label/report it as capability-only. Verify text and URI tags produce one `nfc` input, Wallet VAS does not, and cancel produces no scan. Sources: [Apple NDEF reader app](https://developer.apple.com/documentation/corenfc/building-an-nfc-tag-reader-app), [`NFCNDEFReaderSession`](https://developer.apple.com/documentation/corenfc/nfcndefreadersession).

3. **P3 — Android’s `wallet-vas` capability is not proof of P400 VAS compatibility.** **Confirmed code; physical compatibility unverified.** The snapshot adds `wallet-vas` whenever Android reports NFC hardware (`MainActivity.java:342-352`); actual ISO-DEP is checked only after a tag is presented (`NfcController.java:64-67`). Android documents `IsoDep.get` as null for tags without ISO-DEP and requires apps to implement their own protocol stack. The important counter-control is that `vas.available` remains false and the README/acceptance checklist requires model-specific VAS verification (`android/README.md:34-38`, `android/ACCEPTANCE.md:5-10`). Tera’s [P400 product page](https://tera-digital.com/products/android-13-barcode-scanner-pda-p400) could not be fetched during this audit (HTTP 429); I could not independently confirm its detailed RF/firmware support.
   **Recommendation / acceptance:** Treat `wallet-vas` as protocol capability, not successful device/pass compatibility. Record exact P400 model, firmware, NFC controller, Wallet/pass type, and verifier result; test ISO-DEP absence, wrong pass type, NFC disabled, authentication, and Apple Watch independently. Source: [Android `IsoDep`](https://developer.android.com/reference/android/nfc/tech/IsoDep).

4. **P2 — Hardware barcode support is keyboard-wedge compatibility, not generic accessory access.** **Confirmed source; documented product limitation.** iOS reports `keyboard.connected: null` and `externalReader.mode: keyboard`; the web scanner consumes keystrokes. Android documents HID keyboard input, optional firmware broadcast input, and no raw Bluetooth path (`android/README.md:24-32`); proprietary BLE/SPP requires model-specific integration. Apple’s External Accessory framework is for supported MFi accessories/protocols, not generic scanner discovery. Android USB host APIs can enumerate/communicate with USB devices, but this app does not implement that transport.
   **Recommendation / acceptance:** Keep connection status unknown; market only HID keyboard-wedge support and configured Android broadcasts. Test USB/Bluetooth HID, focus, keyboard layout, suffix keys, leading zeroes, reconnect/sleep, and accidental focus. Do not claim generic serial/BLE support. Sources: [Apple External Accessory](https://developer.apple.com/documentation/externalaccessory), [Apple physical-keyboard events](https://developer.apple.com/documentation/uikit/handling-key-presses-made-on-a-physical-keyboard), [Android USB host](https://developer.android.com/develop/connectivity/usb/host).

5. **P2 — iPad external-camera scanning is plausible but not explicitly selectable or verified.** **Confirmed source + inference; not a proven failure.** The shared decoder supports eight barcode formats (`src/web/scan/camera/decode-worker.ts:6-17`). iOS uses `getUserMedia` with front/back facing preference and discovers only labeled ultra-wide cameras (`src/web/scan/camera/controller.ts:46-59,85-88,161-164`); it does not expose arbitrary `deviceId` selection or handle `devicechange`. A disconnected track fails to `unavailable`, requiring user retry. Apple documents USB-C/UVC external cameras on iPadOS 17+, and WebKit camera access; that does not establish selection/hot-plug behavior here. iOS native camera availability checks only the default AVFoundation device (`ScannerHardware.swift:14-18`). Camera permission is scoped to the trusted main-frame origin (`ScannerViewController.swift:264-273`).
   **Recommendation / acceptance:** If external cameras are a supported iPad workflow, expose device selection and re-enumeration/fallback; otherwise scope the claim to built-in cameras. Test supported USB-C iPads with UVC camera attached before launch, attach/detach during scanning, permission denied, and camera fallback. Do not infer iPhone external-camera support from Apple’s iPad guidance. Source: [Apple WWDC23 external-camera/WebKit guidance](https://developer.apple.com/videos/play/wwdc2023/10106/).

6. **P3 — Duo features are system-gated enhancements, not guaranteed hardware.** **Confirmed source; device behavior unverified.** The iOS shell reads reserved division geometry behind an iOS 27.1 availability check and the web shell consumes it (`ScannerViewController.swift:83-121`; `src/web/scan/ui/scan-shell.tsx:27-42`). The camera-capture accessory separately reports supported/available/active. Apple says the system controls accessory presentation; it requires foreground camera capture and can withdraw it (including when the device folds closed). The implementation’s availability tracking is appropriate; `supported` is an OS/API gate, not proof that a Duo outer display is present.
   **Recommendation / acceptance:** Keep the desk pane and customer display optional. On actual Duo hardware, test unfolded/half-folded/closed, hinge-region geometry, active camera capture, and accessory withdrawal; confirm the normal single-screen scanner remains usable. Sources: [Apple reserved regions](https://developer.apple.com/documentation/uikit/uiview/reservedregions(kind:options:)), [camera-capture accessory on iPhone Duo](https://developer.apple.com/documentation/avfoundation/registering-a-camera-capture-accessory-on-iphone-duo).

**Missing evidence:** No hardware, entitlement-account, provisioning-profile, or runtime behavior was verified. Vendor P400 NFC protocol details remain unconfirmed; no entitlement approval or PSP availability is assumed.
