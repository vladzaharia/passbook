# Security and auth audit (C): wallet Worker

Scope: src/*.ts, src/admin/client.ts, scripts/import-credentials.mjs, deploy.mjs, cloudflare.mjs, wrangler.jsonc, .gitignore, migrations. Read-only. `.secrets/` and `.dev.vars` were not opened (only `ls -l`: all 0600, `.secrets` 0700). Line numbers are from the current tree. Not verified: runtime behaviour (nothing executed), live headers, the Cloudflare Email binding's handling of odd `to` strings, `docs/*.md`, `tests/*`, `live-check.mjs`/`provision.mjs` (skipped by instruction or time).

## 1. Summary
- The current single-tenant code is unusually careful: constant-time comparisons, 244-bit tokens, parameterised SQL everywhere, no `innerHTML`, escaped HTML, bounded outbound fetch with no redirects, safe error and log hygiene. I found no critical or high issues in today's code.
- The main structural weakness is auth: one shared static admin bearer token, no identity, no audit, no revocation except secret rotation, no rate limiting. That is the thing to replace, and it blocks multi-tenancy.
- Medium issues: CSP allows `'unsafe-inline'` for scripts, no HSTS, unbounded device registrations per pass (APNs fan-out DoS), no revocation or rotation of bearer pass links, `..` path traversal in the membership source URL.
- Three latent traps for the target: uploaded templates (ReDoS `pattern`, `template_id` into CSS, `passTypeIdentifier` claiming), connection-URL SSRF, and plaintext credentials in env/D1.
- Recommended target: Pocket ID via OIDC code+PKCE, opaque `__Host-` session cookie backed by D1, Origin-checking CSRF, a confirm-click magic link, hashed API keys, envelope-encrypted connection secrets, and an allow-list/DNS-aware SSRF fetcher.

## 2. What works well (keep)
- `equal()` (util.ts:18-24) hashes both sides with SHA-256 and XOR-compares: constant-time and length-blind. Used for the admin token (index.ts:61) and the Apple `ApplePass` token (index.ts:167).
- Tokens: `randomToken()` (util.ts:17) = two `randomUUID()` (CSPRNG) = about 244 bits. Download and auth tokens are validated as `^[a-f0-9]{64}$` before the DB lookup (index.ts:157). Unguessable; timing on the SQL lookup is irrelevant at this entropy.
- Every query is bound with `?`. The LIKE filter escapes `\ % _` (index.ts:~91). The dynamic `where` is built from constants only.
- No `innerHTML`/`insertAdjacent*`/`outerHTML` anywhere in src/admin/client.ts; DOM is built with `textContent` (client.ts:18-20). Landing and email HTML escape all dynamic values with `escapeHtml` (views.ts, email.ts). The admin token lives only in a JS variable (client.ts:21), not in storage or a cookie. No cookies means no CSRF on `/api`. No CORS headers means cross-origin `fetch` with `Authorization` is blocked by preflight.
- Headers: `nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`, `frame-ancestors 'none'`, `base-uri 'none'`, `form-action 'self'`, `Cache-Control: no-store`, `X-Robots-Tag` (index.ts:23-31). `no-referrer` plus `no-store` is the right posture for bearer URLs.
- Error handler returns a generic 500 with a request id and logs no URL, token or recipient (index.ts:32-38). `observability.logs.invocation_logs=false` (wrangler.jsonc) avoids logging `/p/<token>` URLs in Workers Logs.
- Outbound fetch (sources/http-json.ts): HTTPS-only, `redirect:'manual'` with 3xx treated as failure (so the Authorization header never follows a redirect), 15s timeout, 256 KB streaming cap, content-type check. URL host is deployer config, never holder input. Upstream fields go through `validateInputs`, so an upstream cannot write arbitrary pass.json keys.
- `updatePass` rejects unknown fields (passes.ts:50); `validateInputs` is whitelist-based; `setPath` blocks `__proto__/constructor/prototype` and top-level protected keys (personalize.ts:27-28), and `build()` overwrites `serialNumber/authenticationToken/webServiceURL` after personalisation (passes.ts:21), so input cannot override server-owned fields.
- Optimistic concurrency (If-Match, `version=?` in UPDATE), outbox leases and idempotency keys, bodyLimit 32 KB globally (index.ts:22), serial restricted to `[A-Za-z0-9_-]` (index.ts, so `Content-Disposition` and R2 key are safe).
- Signing refuses a cert/pass identity mismatch (sign.ts:43) and unsafe asset names (sign.ts:49).
- import-credentials.mjs writes 0700 dir / 0600 files with explicit `chmod` (lines 20-28), passes the p12 password via stdin, random 32-byte admin token. deploy.mjs uses `--secrets-file` and deletes it in `finally`. `.dev.vars`, `.secrets/` verified 0600/0700.
- .gitignore covers `.secrets/`, `.dev.vars*` (example whitelisted), `.env*`, `*.p12`, `*.p8`, `*.key`, `*-key.pem`, `.wrangler/`, `dist/`, `public/`, `artifacts/`. A grep for private-key PEM headers outside `.secrets`/`.dev.vars` found only `.dev.vars.example` (placeholder) and `tests/service.test.ts` (test fixture string; not inspected further).

## 4. Not modern best practice
- Shared static bearer admin token entered into a form. Modern: per-person OIDC sign-in, server-side sessions, roles, audit log.
- `'unsafe-inline'` CSP. Modern: nonce-based `script-src 'self' 'nonce-...'`, no inline.
- No HSTS and no edge rate limiting. Modern: HSTS plus Cloudflare Rate Limiting rules/binding and Turnstile on public forms.
- Plaintext link token in D1. Modern: store hashes (or HMAC-derive) so a DB read does not yield capabilities.
- Secrets as flat Worker env vars (signing keys, MEMBERSHIP_API_TOKEN). Fine for one customer; for multi-tenant use Secrets Store for platform secrets and per-tenant envelope encryption in D1.
- Hand-rolled `equal()` hashing: acceptable. Workers also has `crypto.subtle.timingSafeEqual`, which is simpler for equal-length inputs.
- Error responses include HTTPException messages verbatim (index.ts:33); fine now, but sanitise before user-facing multi-tenant use.
- No audit log of admin actions (create/update/void/send email) anywhere in the schema.
- Admin "sign out" is `location.reload()` (client.ts:253): there is no server session to end.

## 5. Recommended auth/security architecture for the target

### 5.1 Identity model (D1)
```
users(id, email_norm UNIQUE, email_verified_at, display_name, created_at, disabled_at)
identities(id, user_id, provider TEXT /* 'pocketid' | 'email' */, subject TEXT, UNIQUE(provider,subject), created_at, last_login_at)
sessions(id_hash PK, user_id, created_at, last_seen_at, idle_expires_at, abs_expires_at, ip_hash, ua_hash, auth_method, roles_snapshot, revoked_at)
oidc_states(state_hash PK, nonce, code_verifier_enc, return_to, created_at, expires_at)   -- or keep in a signed short-lived cookie
magic_links(token_hash PK, email_norm, created_at, expires_at, consumed_at, ip_hash)
orgs(id, name, ...); memberships(user_id, org_id, role)
passes.user_id nullable / pass_recipients(pass_serial, email_norm)   -- link users to passes by verified email
api_keys(id, org_id, prefix, key_hash, scopes, created_by, last_used_at, expires_at, revoked_at)
audit_log(id, ts, actor_type, actor_id, org_id, action, target, ip_hash, request_id, meta_json)
```

### 5.2 Pocket ID OIDC (admin and user sign-in)
- Routes: `GET /auth/login?returnTo=` (relative path only, allow-list check; never full URLs, to avoid open redirect), `GET /auth/callback`, `POST /auth/logout`, `GET /auth/logout/callback`.
- Flow: Authorization Code + PKCE (S256). Generate `state`, `nonce`, `code_verifier`; store hashed in `oidc_states` (or an HMAC-signed `__Host-oidc` cookie, 10 min, SameSite=Lax, since the callback is a top-level GET). Scopes `openid profile email groups`. Confidential client with a client secret stored as Worker secret (PKCE in addition).
- Discovery: fetch `https://id.plrs.im/.well-known/openid-configuration` once per isolate and cache (Cache API / KV, 1 h); pin `issuer` from config and refuse if the document's `issuer` differs. Never accept endpoints from user input.
- Token validation: use `jose` (`createRemoteJWKSet` with the cached `jwks_uri`, works on Workers). Verify signature, `iss`, `aud == client_id`, `exp`, `nonce`, `alg` allow-list (RS256/ES256, never `none`/HS*), `azp` if multiple audiences. Prefer validating the ID token from the back-channel token response; no need to call userinfo unless groups are missing (Pocket ID puts `groups` in the ID token and userinfo when the scope is requested; verify in your instance).
- Roles: configurable `OIDC_ADMIN_GROUP` and `OIDC_USER_GROUP` vars (names or ids). Compute roles at each login: admin if the admin group is in `groups`, user if the user group is. If neither, deny with a clear page (do not auto-create a platform user). Store `roles_snapshot` in the session but re-derive at login only; for fast revocation, set session absolute lifetime short for admins (8 h) and make a `disabled_at` user check on every request. Optionally re-check by calling userinfo with the stored refresh/access token for admins (not necessary at start).
- Identity key = `(provider='pocketid', sub)`, never the email. Pocket ID emails are admin-set, so treat `email_verified` as authoritative only if the claim is true; require `email_verified === true` before linking.
- RP-initiated logout: store the ID token hint (encrypted) or just `id_token` in the session; on logout delete the session, clear cookie, then redirect to `end_session_endpoint?id_token_hint=&post_logout_redirect_uri=` (register that URI in Pocket ID). If Pocket ID does not expose `end_session_endpoint`, local logout only (verify in discovery).

### 5.3 Session design: opaque server-side sessions (recommended)
- Cookie `__Host-sid` = 256-bit random, `Secure; HttpOnly; Path=/; SameSite=Lax` (no Domain). D1 stores only SHA-256 of the id. KV is eventually consistent and bad for revocation; D1 (or a Durable Object per user if you need strict consistency and rate limits) gives immediate revocation, "log out everywhere", and the admin list-of-sessions UI.
- Why not a signed JWT cookie: cannot revoke, group changes and user disable lag until expiry, and you need a rotating key anyway. Cost of D1 session lookup is one indexed read per request; acceptable (optionally cache 30 s in the isolate).
- Lifetimes: user idle 30 d / absolute 90 d (it is a wallet-pass convenience); admin idle 30 min / absolute 8 h; sliding `last_seen_at` update at most once per 5 min (avoid a write per request). Rotate the session id on login and on privilege change (never reuse a pre-login cookie). Re-auth (fresh `auth_time` within 10 min) for sensitive admin actions: API key creation, connection credential changes, template upload, user role changes. Pocket ID is passkey-only, so `prompt=login&max_age=0` gives a cheap step-up.
- Separate cookie scope for admin: serve `/admin` under the same host but require `roles` contain admin; consider a second hostname (`admin.wallet...`) later so a user-side XSS cannot ride an admin cookie. `__Host-` prevents sibling subdomain overwrite.

### 5.4 CSRF
- Cookie-authenticated routes: `SameSite=Lax` (strict for admin if flows allow) plus a server-side Origin/Sec-Fetch-Site check on every non-GET: require `Origin` equal to `PUBLIC_BASE_URL` (or `Sec-Fetch-Site: same-origin`), otherwise 403. Hono: `hono/csrf` middleware covers form content types; write a custom middleware for JSON as well, and require `Content-Type: application/json` on APIs. Add a custom header (`X-Requested-With`) as defence in depth. Double-submit is unnecessary with the Origin check.
- Keep the bearer `/api` surface cookie-free (API keys only) so it is CSRF-immune. Do not let the same route accept both cookie and bearer without the Origin check on the cookie branch.
- OIDC callback and magic-link consume must be bound to the initiating browser (state cookie / link-bound nonce cookie) to prevent login CSRF.

### 5.5 Email magic link
- `POST /auth/email` body `{email}` + Turnstile token (verify server-side via siteverify, bind to action and hostname). Always respond 202 "If that address has passes or an account, we sent a link", with equalised timing (do the DB work and `waitUntil` the send). This resists enumeration.
- Rate limiting: Workers Rate Limiting binding keyed on `email_norm` (e.g. 3 per 10 min) and on IP (e.g. 10 per 10 min), plus a global daily send cap and a D1 per-email counter as fallback (binding is per-location, approximate).
- Token: 256-bit random, store SHA-256 only, TTL 10-15 min, single-use (`consumed_at` set with `UPDATE ... WHERE consumed_at IS NULL RETURNING`). Link: `GET /auth/magic?t=...` shows a "Confirm sign-in" page (no state change, `no-store`, `Referrer-Policy: no-referrer`) and the button does `POST /auth/magic/confirm`. This defeats Outlook/Defender/Gmail prefetch and link scanners consuming the token. Also bind to the requesting browser with a `__Host-ml` cookie set at request time (optional but blocks cross-device phishing relay; if you want "open on phone" UX, skip the binding and show the originating device/IP/time in the confirm page).
- Only send to emails that exist (a user or pass recipient) to avoid being a spam relay; on non-existent addresses send nothing (the same response). Alternatively, allow new accounts only when a pass exists for that email.
- Successful magic-link login sets `email_verified_at` and grants the `user` role only (never admin). Admin access remains OIDC-group only.

### 5.6 Account linking rules
- Primary key is the internal `user_id`; emails are attributes.
- OIDC login: look up `(pocketid, sub)`. If found, use it. If not found and `email_verified===true`, find `users.email_norm`; if a user exists whose email was proven (magic link or earlier OIDC), link the new identity to it. If the existing record is unverified (e.g. created only by an admin entering an email), link only after the OIDC login proves the same verified email (that is the proof). Never link on unverified claims or on a case-only difference without normalisation (lowercase, trim; do not strip plus-tags).
- Magic link into an account that has an OIDC identity: allowed for user role only; admin sessions never created from magic link.
- Email changes: identity `sub` is stable, so a Pocket ID email change updates `users.email_norm` only if it does not collide; on collision, require an admin merge. Changing the email re-evaluates pass linkage: passes are linked by `pass_recipients.email_norm`; do not silently re-link passes to a changed email without verification, and keep old email linkage until the new one is verified. Log in `audit_log`.
- Takeover guard: if an email is reassigned at the IdP to a different person (new `sub`, same email), the pre-existing `(pocketid, sub)` differs, so a second identity would be auto-linked by email. Mitigate by requiring the existing account to have no OIDC identity from the same provider before auto-linking (otherwise require admin approval or magic-link proof).

### 5.7 Pass access
- Keep the direct bearer link (`/p/<token>`) with the fixes in problem 4 (hash, rotate, optional expiry, revoked flag) and expose "rotate link" to the user and admin. Do not let signed-in-user features accept the bearer token as identity.
- Signed-in user: `GET /me/passes` lists passes where `pass_recipients.email_norm = users.email_norm AND users.email_verified_at IS NOT NULL`. Always authorise by joining on user_id/org; every `/api/passes/:serial` query must include the tenant scope (`WHERE serial=? AND org_id=?`) to prevent IDOR once multi-tenant. Force-refresh = `POST /me/passes/:serial/refresh` (CSRF-protected, rate-limited per user and per pass, e.g. 1 per minute; queues a `sync` job; ownership checked).
- Serial numbers: make them random (already UUID default) and per-org unique `(org_id, serial)`; note Apple's `passTypeIdentifier`+`serialNumber` is globally unique in the web service path, so keep serial globally unique or encode org in it.

### 5.8 Admin panel
- `/admin/*` pages and `/admin/api/*` JSON require session with admin role; `requireRole('admin')` middleware in Hono; org-level scoping via `memberships(role)`: `platform_admin`, `org_admin`, `org_viewer` (start with just platform admin and add org roles when the second org appears). Keep group-to-role mapping in config, per-org role in D1.
- Audit log every mutating admin action and every auth event (login success/fail, logout, role denial, API key use). Log ids and hashes, not tokens or full emails if avoidable.
- Cloudflare Access in front of `/admin`: Pros: pre-auth edge gate (the Worker and its parsing code are not reachable by anonymous Internet), WAF-like protection, device posture, can use Pocket ID as an OIDC IdP in Access, Access JWT (`Cf-Access-Jwt-Assertion`) is easy to verify as a second factor. Cons: two overlapping auth layers to debug, free tier user limits (50 seats, fine), the app still needs its own user/role model for `/me`, API keys and magic-link flows (Access cannot front those public routes), and `/api` machine callers need Access service tokens. Recommendation: do the in-app OIDC first (required anyway). Add Access on `/admin*` as defence in depth when convenient, and validate the Access JWT in the Worker (do not trust the header's mere presence). Skip Access for `/p/*`, `/wallet/*`, `/me`, `/auth/*`, and the inbound `/api/v1` key routes.
- Turnstile: on magic-link request and on any unauthenticated form that triggers email. Not needed on the passkey OIDC redirect.
- WAF/rate-limit rules at the edge: 
  - `/auth/*` POST: 10/min/IP. 
  - `/wallet/*` POST/DELETE: 60/min/IP.
  - `/p/*`: 60/min/IP (token enumeration is infeasible at 244 bits, but this blunts scraping and scanners).
  - `/api/*` 401s: 20/min/IP.
  - Managed ruleset + Bot Fight; block non-GET methods with bodies above 64 KB except the template upload route.

### 5.9 Machine API (inbound updates from external systems)
- Separate from sessions. `Authorization: Bearer wlt_<prefix>_<secret>`; store `prefix` (lookup) and SHA-256 of the secret (a fast hash is fine for 256-bit random keys), per-key `org_id`, scopes (`passes:write`, `passes:read`, `sync:trigger`), optional IP allow-list, `expires_at`, `last_used_at`, shown once at creation, revocable, rotation with overlap (two active keys). Constant-time compare on the hash. Rate-limit per key. Every call is audit-logged with the key id.
- Idempotency-Key and If-Match semantics (already present) should be kept on the v1 API. Webhook-style inbound endpoints should accept HMAC-signed bodies (`X-Signature` with timestamp, 5 min window) if the sender cannot hold a bearer key safely.

### 5.10 Connection credentials (outbound API connections)
- Ranking: (1) Cloudflare Secrets Store is good for platform-wide secrets (OIDC client secret, KEK, Turnstile secret) but is per-account bindings declared in config, not dynamic per-tenant. (2) Workers secrets: same limitation, not usable for runtime-added tenant credentials. (3) Envelope encryption in D1: use for tenant credentials. Generate a random 256-bit DEK per secret, AES-256-GCM encrypt the value with AAD = `org_id|connection_id|version`, wrap the DEK with a KEK held as a Worker secret (support `kek_id` for rotation). Store `{kek_id, wrapped_dek, iv, ciphertext}`. Decrypt only inside the sync job; never return the value through any API or log (write-only fields in the UI; show last 4 chars). Re-wrap on KEK rotation.
- Credentials get an `allowed_host` bound at creation, so a credential cannot be replayed against a different host by editing the URL.

### 5.11 SSRF protection for admin-configured URLs
- Workers `fetch` cannot reach private RFC1918 ranges or the Cloudflare network internals directly, which removes the classic metadata-IP risk, but you can still hit other Cloudflare-hosted/public targets, your own zone (loopback to your own Worker via public hostname), and internal services exposed via Tunnel/VPC bindings. Defences: HTTPS only, port allow-list (443, optionally 8443), reject IP literals, `localhost`, `*.internal/.local`, credentials in URL, and the platform's own hostnames (wallet.plrs.im, id.plrs.im, `*.workers.dev`); resolve DNS via DoH (`cloudflare-dns.com/dns-query`) at save time and at run time and reject private, loopback, link-local, CGNAT and ULA results (DNS rebinding is partly mitigated because fetch resolves separately, so pin by checking again immediately before fetch and treat it as best-effort); `redirect:'manual'` and only follow after revalidating the new URL against the same rules, never forward the Authorization header across origins; response caps (size, time, content-type, JSON depth); per-connection rate limit and concurrency; no response bodies echoed back to admin on error (generic status only, otherwise a blind-SSRF read primitive); only admins of the org may create connections and creation is audit-logged.
- Path parameters from pass data (the `reference`) must be validated as shown in problem 6 and never allowed to alter host, scheme or userinfo.

### 5.12 Template upload safety (zip / .pkpasstemplate)
- Enforce at the edge with `bodyLimit` on that route only (e.g. 5 MB), `Content-Type` check, and stream to R2 first, then process in a Queue consumer. Parse with fflate `unzipSync` using the `filter` option to inspect `originalSize` before inflating; limits: max 200 entries, max total uncompressed 20 MB, per-file 5 MB, compression ratio under 100:1, nesting none. Reject names with `..`, leading `/`, backslashes, NUL, absolute or drive paths, symlinks, duplicate names, case-insensitive collisions, and anything outside the allowlist (`pass.json`, `*.png`, `*.strings` in `*.lproj/`, as sign.ts:49 already does). Never extract to a filesystem; keep in memory only.
- PNG: validate magic bytes and IHDR, cap dimensions (e.g. 2000x2000) and pixel count before any decode, do not decode in the Worker unless needed (the .pkpass only needs bytes); if thumbnails are needed use Cloudflare Images. Strip nothing, serve only as `image/png` with `nosniff`.
- pass.json: parse with size cap and depth cap (reject depth over 12); reject `webServiceURL`, `authenticationToken`, `serialNumber` in the upload (server-owned); force `passTypeIdentifier`/`teamIdentifier` to match the org's registered signing identity, not what the template says (sign.ts:43 already checks cert match, but a tenant must not pick another tenant's identity); validate `barcodes`, `featuredActions` URL schemes (https/tel only, sign.ts:36), and `locations` count (max 10).
- Template mapping: replace free-form `pattern`, `paths`, `fieldKeys` with a restricted declarative schema validated at upload (patterns from a fixed set of formats or re2-safe; JSON-pointer paths whitelisted against the template's own pass.json and never top-level protected keys; test-render on upload within a CPU budget). Version templates immutably; the template id must be a slug `^[a-z0-9-]{1,40}$`.
- Treat the uploader as semi-trusted: org-admin only, audit-logged, with a "preview" that renders in the sandbox `Content-Security-Policy: sandbox` / separate origin if you ever show their HTML.

### 5.13 Quick wins before the rewrite
1. Remove `'unsafe-inline'` from `script-src`; add HSTS and Permissions-Policy.
2. Registration cap + token format + edge rate limits for `/wallet/*`.
3. `reference` validator; strict single-address email parser.
4. Hash/rotate download tokens; add `revoked_at`.
5. Introduce `audit_log` and Rate Limiting binding now so the new auth lands on top of them.

## 6. Open questions for the owner
1. Does Pocket ID at id.plrs.im expose `end_session_endpoint`, and does it include `groups` in the ID token or only userinfo? Can it issue a confidential client with `email_verified` accurate for all users?
2. Group names: exact admin and user group names (or ids), and should a person with neither group be denied entirely, or fall back to magic-link user access?
3. Who may be an admin: only the platform owner, or per-organisation admins too (changes the role model and Pocket ID group layout, e.g. `org:<slug>:admin`)?
4. Do users need to be able to sign in at all before they own a pass (self-registration), or only when an admin has linked an email to a pass?
5. Should a bearer pass link keep working forever, or expire/rotate (e.g. on voided pass, after N months, on user request)? Are old emailed links allowed to break?
6. Is a second hostname for admin (`admin.wallet.plrs.im`) acceptable for cookie isolation? Do you want Cloudflare Access in front too?
7. Expected tenant isolation requirements: is one org's admin ever allowed to see another's passes/templates/connections? Does each org bring its own Apple Pass Type ID certificate (private key custody becomes your liability, so envelope encryption plus audited access is mandatory) or share the platform's?
8. For machine API connections: which auth do the external systems support (bearer, HMAC, OAuth client credentials, mTLS), and are their hosts known/static (allow-list per tenant) or arbitrary?
9. Acceptable email volume and providers for magic links (Cloudflare Email Sending limits, sender reputation), and is Turnstile acceptable UX on the sign-in form?
10. Retention and privacy: how long to keep audit logs, sessions, and old signed pass versions in R2 (member names and barcodes are personal data)?
